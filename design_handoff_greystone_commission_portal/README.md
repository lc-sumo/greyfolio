# Handoff: Greystone Commission Portal

## Overview

A commission tracking portal for Greystone Merchant Partners (MCA / business-funding broker). Two audiences share one app:

- **Reps** log in and see only their own deals, their split, what they've been paid, what they're owed, and any clawbacks against them — presented as a running "wallet" balance.
- **Finance ops / admin** manage the master deal board, run payroll per rep by selecting specific deal lines, track renewals and merchant records, configure lenders/partners/products/teams/reps, and operate the Google Sheets and QuickBooks integrations.

The portal is intended to replace a Google Sheets / Excel tracker (`GREYSTONE TRACKER - CLEAN TEMPLATE.xlsx`, included for reference) while continuing to mirror to that sheet.

## About the Design Files

The files in this bundle are **design references created in HTML** — a working prototype showing the intended look, information architecture, and behavior. **They are not production code to copy directly.**

`Greystone Commission Portal.dc.html` is a single-file prototype with all state held in browser memory and all data generated by a seed function. There is no backend, no auth, and no persistence.

**The task is to recreate these designs in the target codebase's environment**, using its established patterns and libraries. Greystone already has a partial codebase (see "Existing Codebase" below) — a Postgres + Drizzle schema, an Express API server with OIDC auth, and a React/Vite front-end with shadcn/ui primitives. Build there rather than starting fresh.

⚠️ **The most valuable part of this handoff is not the markup — it is the "Domain Model & Business Rules" and "Accounting Invariants" sections below.** Those rules were derived iteratively and several of them are non-obvious. Getting them wrong produces a portal where the same rep is owed two different amounts on two different screens. Read those sections before writing code.

## Fidelity

**High-fidelity.** Final colors, typography, spacing, and interaction behavior. Recreate the UI faithfully using the codebase's existing component library, substituting shadcn/ui primitives where they match. The layout logic (grid column definitions, min-widths, overflow containers) is deliberate — see "Layout Constraints That Matter".

## Domain Model & Business Rules

### 1. Opportunity vs. deal vs. segment

This is the core modeling decision and it is easy to get wrong.

- An **opportunity** is one funding relationship and has **one deal ID** (format `F1`, `F2`, … — matches the sheet's `="F"&COUNT(...)` formula).
- For MCA/term/equipment products, the opportunity is a single funding event.
- For **LOC and consolidation** products, the merchant draws repeatedly against a facility. **Ten pulls on one LOC are one opportunity with ten draw lines — not ten deals.** The deal ID does not change.
- A **segment** is any commissionable event on an opportunity: the initial funding (`sk: 'base'`) plus each draw (`sk: 'D1'`, `'D2'`, …). All commission math, collection tracking, and payroll lines operate at the **segment** level.

```
Opportunity F12  (LOC - INITIAL, lender ROWAN)
├── segment 'base'  initial draw $40,000 @ 8%  → gross $3,200
├── segment 'D1'    draw        $25,000 @ 4%  → gross $1,000
└── segment 'D2'    draw        $18,000 @ 4%  → gross   $720
```

Draw commission rates differ from the initial: each multi-draw product carries an **initial draw %** and a **subsequent draw %**. A new draw immediately adds a line to outstanding commission.

Separately, a deal may carry an optional **`parentId`** linking a separately-entered funding to an existing opportunity (for cases where multiple fundings on one facility were keyed as distinct deals).

### 2. Commission calculation

Per segment, in order:

```
basisAmount   = product.basis === 'payback' ? funded × factor : funded    // or draw amount
commission$   = basisAmount × commissionRate
psf$          = basisAmount × psfRate
gross$        = commission$ + psf$ + originationFee
referralFee$  = min(gross$ × referralRate, partner.monthlyCap)            // cap applies
net$          = gross$ − referralFee$
openerPayout  = net$ × openerRate
closerPayout  = net$ × closerRate
overridePayout= net$ × overrideRate
totalRepPayout= opener + closer + override
houseNet      = net$ − totalRepPayout
```

`product.basis` is one of `funded` | `draw` | `payback`, configurable per product.

Payback: `funded × factor` for factor-rate products; `funded × (1 + apr/100 × termDays/252)` for amortizing products (252 business days/yr).

### 3. Splits

- Every deal has an **opener**, a **closer**, and an optional **override rep** (the team leader). These are independent — Michael can open and Noah can close, and each sees only their own contribution.
- Rates default from the rep's profile (`openerRate`, `closerRate`, `overrideRate`) and are **overridable per deal**.
- The override rep defaults from the opener's team leader.
- Terminology matches the workbook: **Opener / Closer / Override** (columns `Opener %`, `Closer %`, `Override %`).

### 4. Commission collection (weekly increments)

Commission terms are a property of the **lender**, not the product:

- `terms: 'upfront'` — the whole commission is collected on funding.
- `terms: 'weekly', weeks: N` — the lender pays commission in N equal weekly increments. Common for consolidations.

A segment on a weekly lender carries a schedule `{ mode: 'weekly', weeks, received, startDate }`. `received` is how many weekly increments have actually landed.

### 5. Clawbacks

- Policy: **the rep repays their full share of that deal's commission.**
- A clawback record carries `amount` (deal-level), and a `recovered` amount tracking how much has already been withheld.
- A rep's slice of a clawback is proportional: `repShare × (clawback.amount / totalNet(deal))`.
- The unrecovered remainder nets against the rep's next payout. **It must only be collected once** — see invariant #3.

### 6. Payroll

- Cycle: **twice monthly** (configurable).
- Ops picks a **run**, then a **rep**, then checks **which specific deal lines** to pay. A line is one role on one segment (`F12|Opener|D2`).
- Selecting lines shows gross selected, clawback netted, and net to pay. Paying writes ledger rows and, if every line on every segment of a deal is now paid, stamps the deal's `repPaid`.
- Ops can search the payable lines by **deal ID, business name, merchant contact name, merchant email, or merchant phone**.
- Each line displays whether the lender has actually paid that commission (`14/20 wks` for weekly, `Collected` / `Part collected` / `Not collected` otherwise), and the footer warns by deal ID when paying against uncollected commission.

### 7. Rep-scoped visibility

A rep must **never** see:
- House net / company margin
- Referral partner or referral fee
- Override amounts (the manager's cut)
- Other reps' names on shared deals (the leaderboard anonymizes everyone but them)

A rep **does** see: funded amount, their role(s), their rate(s), their share, payment status, and their own clawbacks.

The admin has a **"View as"** control that renders the exact portal a given rep sees — implement this as a server-side scoped query, not a client-side filter.

### 8. Renewals

A deal becomes **renewal-ready** at the configurable **renewal mark** (default 40% of payback paid in). Buckets: renewal-ready, inside 21 days of the mark, building, blocked (slow pay/default), refinanced.

## Accounting Invariants

These are non-negotiable. Every one of them was violated at some point during design and produced two screens disagreeing about a rep's money.

**1. There is ONE definition of a rep's money.**
Implement a single `repLedger(repId)` returning `{ earned, paid, cash, held, recovered, owed }`. The rep wallet, the rep's cards, the admin roster, and payroll netting must all read it. Never re-derive any of these independently.

```
earned  = Σ over rep's deals of (rep's rate × totalNet(deal))
paid    = Σ of payment-ledger rows where amount > 0        // GROSS settled
cash    = Σ of ALL payment-ledger rows                    // net of recoveries
held    = Σ over OPEN clawbacks of remaining slice
owed    = max(0, earned − paid − held)
```

**2. "Paid" ALWAYS comes from the payment ledger — never from deal status.**
Deriving paid from `commissionStatus === 'YES - Paid In Full'` will disagree with the ledger. This was the single most repeated defect.

**3. A clawback recovery is a cash event and MUST write a ledger row.**
When a clawback is recovered, write a negative `Clawback recovery` row to the payment ledger, split across the roles that earned the deal. If recovery is only a status flag, `paid` (gross) and `cash` (net) drift apart by exactly the recovered amount and no two screens will agree. Also: net `held` against `remaining = share − recovered`, never against the full share, or the rep is charged repeatedly on every subsequent run.

**4. Balance must net against SETTLED GROSS, not net cash.**
`owed = earned − paid(gross) − held`. Using `cash` (which includes negative recovery rows) hands an already-withheld clawback back to the rep as available balance.

**5. Collection is ONE quantity: dollars received from the lender.**
Not a boolean, not a status. Weekly segments derive it from `gross × received/weeks`; others store it explicitly.

```
statusFor(collected, gross) =
  collected >= gross  → 'YES - Paid In Full'
  collected > 0       → 'Partially Paid'
  else                → 'Waiting for payment'
```

**Commission status is a FUNCTION of collection, never a peer field.** The status dropdown must *write collection* (Paid In Full → `received = weeks`), not set a status alongside it. Otherwise a deal reads "paid in full" and "70% collected, $1,164 outstanding" simultaneously, and the next recorded week silently reverts the manual status.

**6. A "paid" figure must never render negative.**
Sum only positive ledger rows for display and surface the withholding as its own line ("less $672 clawback recovered"). A period containing only a recovery otherwise shows the rep as paid −$672.

**7. Earned and paid are on DIFFERENT time axes.**
Earned buckets by the month the deal **funded**; paid buckets by the date the payout **cleared**. Charting both on one axis is wrong. Label them explicitly.

**8. Never allow a funded date in the future.**
This is the *funded* board, not a pipeline. Reject at entry rather than filtering downstream — a future-dated deal silently drops out of period filters and makes lifetime and YTD totals disagree.

**9. Deactivating a rep must not alter historical assignments.**
Three different option lists are needed:
- New-deal assignment (opener/closer/override) → **active reps only**
- Editing splits on an **existing** deal → **all reps**, inactive suffixed `(inactive)`
- Admin View-as → **all reps** (you need to open a departed rep's portal to settle a final balance)

A controlled `<select>` whose value is missing from its options renders as "— none —", and an admin will "correct" it — reassigning commission away from the rep who earned it.

## Interactions & Behavior

- **CRM deep link** — built from a template with tokens `{id}`, `{opportunity}`, `{business}`; URL-encode each. Renders as "Open in CRM ↗" in the deal panel and a small ↗ beside the deal ID in the master grid, `target="_blank" rel="noopener"`. Blank template hides all CRM links.
- **View as** — sidebar select; renders the rep's exact portal. Server-scope it.
- **Lender-paid pill** — on a weekly deal, click records the next week; on an upfront deal it toggles fully collected. Both route through the single collection setter.
- **Commission status select** — writes collection (see invariant #5).
- **Add draw** — prices at the subsequent rate, appends a segment, immediately increases outstanding.
- **Pay selected** — writes ledger rows, allocates clawback recovery across open clawbacks oldest-first, writes negative recovery rows, pins the selected rep, and stamps `repPaid` only when every line on every segment is paid.
- **Toasts** — bottom-center, `#242931`, 12px/20px, 10px radius, auto-dismiss 2.6s.
- **Drawers** — right-side, `min(620px,100%)`, `rgba(20,24,32,.42)` scrim, `-20px 0 60px rgba(20,24,32,.18)` shadow, click-outside closes.
- **Body animation** — `gsRise` 0.4s ease (opacity 0→1, translateY 8px→0) on view change.
- Guards that must survive: in-use lenders/partners/products refuse deletion with a count; teams refuse deletion while staffed; new deal requires business + amount + lender, and a parent when the product demands one.

## State Management

Server state (React Query or equivalent): deals + draws, reps, teams, payout lines, clawbacks, payroll runs, settings, sheets sync state.

UI state: `view`, `settingsTab`, `viewAs`, `period` (7d/30d/QTD/YTD), `search` / `payrollSearch` / `renewalSearch` / `merchantSearch`, `statusFilter`, `repFilter`, `renewalFilter`, `activeRunId`, `payrollRepId` (**pin on commit** — see below), `selected` line map, `openDealId`, `openMerchant`, `newDealOpen`, `draft`, `drawAmount`, `toast`.

⚠️ **Pin the payroll rep when committing a payment.** If the screen resolves its default rep as "whoever is owed most", paying that rep zeroes their balance and the panel silently re-targets a different rep — destroying the payment confirmation and risking a second payment to the wrong person.

## Layout Constraints That Matter

These caused real defects; keep them:

1. **Every wide table lives in `overflow-x:auto` with an inner fixed `min-width`.** When you add a column, raise that min-width.
2. **A grid column containing a wide table must be `minmax(0,1fr)`, never `1fr`.** Bare `1fr` is `minmax(auto,1fr)` and, with the default `min-width:auto` on grid items, cannot shrink below the table's min-content — the overflow escapes to the document and the whole page slides sideways while the table's own scroller sits unused.
3. **Flexible text columns need real floors** (`minmax(170px,1.2fr)`), or they absorb the shortfall and crush to ~50px.
4. **Status columns must be `minmax(0,1fr)` with `white-space:nowrap` on their pills**, or each row resolves a different width and the column stops aligning with its header.
5. **Totals rows belong inside the scroller as the table's last grid row**, not as a sibling under it.
6. Long text cells: `min-width:0` + `white-space:nowrap` + `overflow:hidden` + `text-overflow:ellipsis`.

- Sheet → Portal is read-only *staging*: detected cell edits are queued for accept/discard and never overwrite portal data automatically.
- Map to the existing tabs: `FUNDED DEALS` (the 48-column master), `REP COMMISSION`, `REP MONTHLY`, `DEAL TRACKER` (LOC/consolidation roll-ups), `SETTINGS`, `REPS`, `PARTNERS`, plus new `Payroll` and `Payroll — Paid Lines` tabs.
- Use a service account + Sheets API v4; store `spreadsheetId` and a per-tab revision/hash for change detection.

**QuickBooks Online** (the user left scope unanswered; this is the proposed default — confirm before building)
- Approved rep payout → **vendor bill** (1099 contractor), Commission Expense 6110
- Approved payroll run → **journal entry**, Commission Payable 2210
- Lender commission received → **invoice + deposit**, Commission Income 4010
- Clawback → **vendor credit memo**, Commission Expense 6110
- Bill payment cleared → **read back** into the portal
- Every memo line carries the deal ID so QBO reconciles back to the portal. Nothing posts until a run is approved. OAuth2; each rep must exist as a vendor with a W-9.

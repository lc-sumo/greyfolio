## Decisions that need a reviewer's eye

1. **The existing code package is not in this repo.** The README says to extend `lib/db/src/schema/commission.ts` from `greystone-code-package.zip`. The `greyfolio` repository was empty, so the schema here defines the full tables (README "existing" columns + Phase 1 additions) at the same path. When the original package is available, diff column names and keep the originals where they differ. No `commission_payments` table was created: the ledger (`commission_payout_lines`) is the only "paid" source, and a second payments table is exactly the kind of peer field invariant #2 forbids.

2. **Per-rep clawback recovery is read from the ledger, not from `clawback.recovered`.** `repClawback` sums the rep's negative `Clawback recovery` rows for that clawback. `clawback.recovered` is kept (README schema) as the deal-level roll-up and is written in the same transaction (`planPayout` returns `clawbackUpdates`). A test asserts the two agree. This makes "collected exactly once" structural rather than a status flag.

3. **Clawback status is derived**: `recovered` once every rep's slice is withheld (the prototype flipped it after a single rep's share, which mis-closes multi-rep clawbacks).

4. **Commission status is not stored** on deals or draws. The README's draw table lists a `status` column; per invariant #5 it is computed by `dealCommissionStatus` / `segmentStatus` and pushed to the sheet as a derived column.

5. **Rep payouts are `net × rate`** (README §2), but the workbook computes `Opener $` etc. as **gross × rate** (`=O4*U4`) and its referral fee as **(gross − PSF) × rate**. The portal follows the README. If the workbook is authoritative, both are one-line changes in `commissionFor`.

6. **Referral cap** is implemented as a per-partner *monthly* cap (`referralFeeFor` accepts `paidThisMonth`); with nothing passed it reduces to the README's `min(gross × rate, cap)`.

7. **Money is dollars rounded to cents**, not whole dollars as in the prototype. Every line amount is rounded before summing, so earned equals the sum of its lines exactly.

8. **Emails are placeholders** (`first.last@greystoneus.com`). The workbook has none. Do not let Phase 2 OIDC auto-link on them until confirmed.

9. **Roles**: only Leor is seeded as `admin`; everyone else is `rep`. Team leads / managers are open question #4.

10. **Seed values the workbook does not carry** (marked `// assumption` in `workbook.ts`): lender terms (ROWAN 20 wk, ENOD CAPITAL 12 wk, Lendini 16 wk from the prototype; MILVADO CAPITAL and Cetan Funds set upfront), product rules for the three draw/disbursement products, `REVERSE - TOTAL FUNDING` marked multi-draw because the sheet treats it as a parent, and the `NONE` partner at 10% (verbatim from the sheet, looks like a data-entry oddity).

11. **CRM URL template seeds blank**, which hides every CRM link until the real pattern is supplied (open question #6).

12. **Weekly schedules on draws**: `newDraw` accepts an optional schedule and `scheduleFor(lender)` builds one, so either answer to open question #2 is a one-line policy in the API.

13. **Partial upfront receipts**: the domain never guesses. `withStatus(seg, 'Partially Paid')` keeps an existing partial figure or takes an explicit dollar amount; the only 50% default lives in the import-time helper `collectedFromSheetStatus` (open question #7).
